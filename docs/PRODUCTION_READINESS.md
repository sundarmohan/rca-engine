## Files and deployment boundary

[compose.ingress.yaml](../compose.ingress.yaml) is a separate Caddy project. [Caddy](../deploy/Caddyfile) proxies host loopback `127.0.0.1:8000`; PostgreSQL is separate. Deployment requires domain/contact configuration, localhost app binding and a distinct >=32-character operator token before exposure. Actual development HTTPS, HTTP redirect, headers, public auth/docs boundaries and external private-port checks passed. Renewal, host hardening and rollback acceptance remain open. These checks are not production approval.

[scripts/deploy.py](../scripts/deploy.py) always runs Caddy configuration validation on EC2 before replacing the application, including deployments without public ingress. For that validation only, absent values default to `rca.example.invalid` and `ops@example.invalid`. The validation command does not start a Caddy server or prove certificate issuance/DNS reachability. Without configured ingress, no new public Caddy server starts. When configured, deployment starts the separate ingress project after app readiness/smoke checks and checks public HTTPS readiness with certificate verification enabled.

Do not merge the ingress file into the application composition. Use the independent project name `rca-ingress`; preserve the relative Caddyfile path and the project-owned named volumes across releases. Deployment orchestrates both projects while keeping their service lifecycle and storage separate. When invoked directly, this composition rejects missing or empty `RCA_PUBLIC_DOMAIN` or `RCA_TLS_EMAIL`; Compose does not validate their format, operator-token strength or app binding. Clearing variables alone does not stop a previously running container: explicitly stop Caddy when withdrawing ingress and verify that behavior on EC2. Deployment implements restoration of prior managed ingress or stopping newly started ingress on failed rollout where applicable; rollback evidence remains pending. The manual procedure below also supports a stable ingress directory outside app release directories.

## Administrator prerequisites

- Use a Linux EC2 host with Docker Engine and Compose v2. Host networking shares host listeners and loopback; bridge-network port publishing is not used.
- Confirm the deployed app binds **only** `127.0.0.1:8000` (`APP_BIND_HOST=127.0.0.1` through deployment configuration). PostgreSQL must remain on loopback `5432`. Optional ingress integration requires localhost binding and a distinct operator token of at least 32 characters before server start; verify the actual EC2 runtime. Caddy itself does not enforce token configuration or correct an app previously configured with `0.0.0.0`; direct app access bypasses proxy limits and headers.
- Configure one public DNS hostname owned by the operator. `RCA_PUBLIC_DOMAIN` must contain only that hostname, such as `rca.example.com`: no scheme, port, path, wildcard, spaces, newlines or Caddy configuration syntax. Treat both ingress variables as trusted administrator configuration; do not derive them from request data. `RCA_TLS_EMAIL` must be a valid monitored contact address.
- Point DNS A records to the host's stable public address. Publish AAAA only when IPv6 reaches the same host. Check CAA permits the configured/default ACME issuer. No DNS provider credentials or DNS challenge plugin is supplied.
- The user's cloud/network administrator must configure security groups, host firewall and any network ACLs for inbound **TCP 80 and 443**, with intended source restrictions. Port 80 supports HTTP redirects and ACME HTTP challenges; port 443 supports HTTPS/TLS challenges. Public CA validation must be reachable. UDP 443 is unnecessary because HTTP/3 is disabled. Do not expose 8000, 5432 or a Caddy admin port. Restrict SSH to approved management sources.
- Confirm no other host service occupies 80/443. Allow necessary egress for DNS, ACME certificate issuance/renewal and image retrieval. Maintain accurate host time.
- Before enabling public ingress, resolve the missing human authentication and webhook controls or use a restricted staging network with synthetic data. Configuring a domain enables a public UI and public health endpoints; bearer tokens protect API data only.
- Require IMDSv2, restrict metadata access and set a suitable hop limit for the actual host-network workload. Host-network Caddy can reach metadata and local host services; containers are not a network isolation boundary. Supply no cloud credentials to Caddy and keep the instance role least privilege.
- Establish host patching, reviewed Docker/image updates, disk monitoring, secrets handling and backup/restore ownership. Docker group access is root-equivalent.

These are administrator prerequisites, not cloud mutation instructions. This change contains no DNS, IAM, security-group or other cloud mutation script.

## Caddy controls and limitations

- Image is pinned to `caddy:2.10.2-alpine`, not a floating tag. A version tag is not an immutable digest or evidence of a vulnerability review. Record the pulled digest and review advisories before approval; version changes require a reviewed update.
- Caddy manages public certificate issuance, renewal and HTTP-to-HTTPS redirects. The persistent `rca-ingress_caddy_data` volume contains certificates, ACME account material and private keys; `rca-ingress_caddy_config` is also persistent. Keep both across updates/rollback. Neither volume stores application report history.
- The standard image runs explicitly as root (`0:0`), with all capabilities dropped except `NET_BIND_SERVICE` for privileged ports. This is a documented exception to the objective's non-root requirement, **not non-root hardening**. The root filesystem and Caddyfile mount are read-only; only `/data`, `/config` and the bounded `/tmp` tmpfs are writable. Standard root-owned named volumes are writable without adding ownership-changing capabilities. A future non-root variant must prove image UID/GID, volume provisioning and privileged binding on EC2; changing `user` alone is insufficient.
- `no-new-privileges` is enabled, the admin API is disabled, and no Docker socket, application runtime secrets, database path or cloud credential path is mounted. Host networking still permits access to host-local services. The exception needs security-owner acceptance for any production rollout.
- Body limit is **65,536 bytes (64 KiB)** on proxied requests, including streamed bodies as they are read. It is not a complete application memory, response-size, rate or concurrency budget. Redirects and ACME challenge handling belong to Caddy's automatic HTTPS subsystem rather than the proxied app route.
- Limits: 16 KB request headers; 10-second header reads; 30-second body reads; 60-second server writes; 2-minute idle connections. Proxy dialing is 5 seconds, response-header waiting 40 seconds, and upstream reads/writes 30 seconds. Cloud operations have a 30-second service response timeout; the browser allows 35 seconds for cloud API requests (20 seconds for other requests). Stream I/O limits are not a centrally enforced total investigation deadline. Long operations may time out after having reached the app; review reports before retrying event/email requests. No automatic proxy retry is configured.
- HSTS lasts one year for this hostname, without preload or `includeSubDomains`. Other headers deny framing, disable MIME sniffing, suppress referrers, disable camera/microphone/geolocation, prevent caching and constrain content to same origin. The existing UI uses same-origin assets. Public `/docs`, `/redoc`, their subpaths and `/openapi.json` return 404; use the private SSH tunnel for Swagger when the app enables it. The app disables docs entirely in production.
- Caddy access logging is off; HTTP request error logs are excluded to avoid capturing URLs/headers. Runtime warnings/errors remain and may identify the domain or certificate failures. Container logs rotate at 10 MB with three files. This reduces HTTP diagnostic visibility; use synthetic probes and sanitized operational counters. It does not redact the app's existing Uvicorn access logs, host logs or third-party logs.
- Upstream is fixed cleartext HTTP over host loopback. There is no upstream certificate verification to disable, and no certificate-disabled TLS option. Forwarded identity headers are replaced with the direct connection's information; no external trusted proxy is configured. A future load balancer requires a separate trusted-proxy review.

## EC2-only operator commands

Deployment runs the optional ingress automatically after its eligibility checks; unconditional EC2 configuration validation also runs when ingress is unconfigured, without starting a server. For manual EC2 validation/operation, run these only after the same prerequisites and staging exposure review, including the distinct operator-token and localhost-binding checks. Example working directory is the administrator's stable ingress directory containing [compose.ingress.yaml](../compose.ingress.yaml) and [deploy/Caddyfile](../deploy/Caddyfile). Use actual administrator-approved values:

```bash
export RCA_PUBLIC_DOMAIN='rca.example.com'
export RCA_TLS_EMAIL='ops@example.com'
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml config --quiet
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml pull caddy
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml up -d --no-build caddy
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml ps
curl --fail --show-error http://127.0.0.1:8000/ready
curl --fail --show-error "https://${RCA_PUBLIC_DOMAIN}/ready"
curl --silent --show-error --output /dev/null --dump-header - "http://${RCA_PUBLIC_DOMAIN}/"
curl --silent --show-error --output /dev/null --dump-header - "https://${RCA_PUBLIC_DOMAIN}/"
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' "https://${RCA_PUBLIC_DOMAIN}/docs"
```

Expected: configuration and Caddy validation succeed, app readiness reports `storage: postgresql`, HTTPS validates against the system trust store, HTTP redirects to HTTPS, security headers are present, and public docs return 404. Never bypass certificate verification. Caddy has no container healthcheck here; a running container is not proof of TLS or upstream health. Validate first against a restricted staging hostname, and avoid repeatedly issuing public certificates during troubleshooting.

Also verify listeners with `ss -lntp` on EC2 and check external reachability from another approved machine. Confirm 8000/5432 are inaccessible externally, unknown hostnames do not reach the app, missing/empty ingress variables fail Compose validation in a separate shell, invalid tokens are rejected, and public assets/health have the documented public behavior. Confirm spoofed forwarding headers are replaced and Caddy's admin listener is absent. Capture sanitized evidence of effective UID, capabilities, mounts and read-only filesystem without dumping application environment values.

For the size limit, use synthetic data on EC2: compare exactly 65,536-byte and 65,537-byte bodies and chunked transfer to a proxied endpoint. An unauthenticated request can fail authentication before the entire stream is read; an authenticated synthetic event should be used to prove streaming rejection and that oversized input does not create a report. Expect 413 for the oversized case; valid-size malformed JSON may return 422. Keep the token in a protected client configuration, never a URL, transcript or checked-in file. Check slow-body/header behavior, upstream failure/timeout, browser CSP compatibility, certificate renewal and log absence using synthetic traffic.

For update/rollback, preserve a reviewed copy of the two ingress files, record the image digest, and validate the reviewed configuration before recreating Caddy with the same project and volumes. Restore the prior pair/image version and repeat validation/health checks on rollback. Since the admin API is off, apply changes with recreation; allow for brief HTTPS interruption. Do not remove volumes or use volume-deleting teardown. To withdraw ingress while retaining certificate storage:

```bash
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml stop caddy
docker compose --project-name rca-ingress --env-file /dev/null -f compose.ingress.yaml logs --tail 50 caddy
```

Protect runtime log output before sharing. The ingress rollback does not roll back the app or PostgreSQL. Use the existing deployment runbook for managed application rollback after review of its administrative behavior.
